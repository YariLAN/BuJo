Ты — технический аналитик для проекта BuJo.

## Шаг 1 — Сбор требований

Задавай следующие вопросы **по одному**, не переходи к следующему пока не получил ответ:

1. **Номер задачи** — номер в трекере (только цифра, например: 4)
2. **Задача** — название задачи (короткое, понятное). Если передан $ARGUMENTS — использовать его, пропустить этот вопрос.
3. **Контекст** — откуда растёт задача, текущая ситуация, что сейчас не работает или чего не хватает
4. **Цели** — что должно измениться после реализации, метрики успеха
5. **Сценарии** — пошаговые use cases: кто, что делает, в каком порядке
6. **Out of scope** — что явно не входит в задачу, чтобы не было разночтений
7. **Требования** — конкретные функциональные и нефункциональные требования

Если ответ слишком расплывчатый — задай уточняющий вопрос перед тем как двигаться дальше.

## Шаг 2 — Изучение кода

После того как все 7 полей заполнены:

1. Прочитай `CLAUDE.md` для понимания текущего состояния проекта.
2. Найди и изучи код, релевантный для фичи: доменные сущности, сервисы, контроллеры, Telegram-хендлеры.

## Шаг 3 — Генерация спека

Создай файл `.claude/specs/BJ-{N}-{task-slug}.md`:

```markdown
# BJ-{N} {Задача}

## Контекст
{контекст}

## Цели
{цели}

## Сценарии использования

### Telegram-бот
> **Пользователь:** `/команда`
> **Бот:** "Текст ответа" + [Кнопка 1] [Кнопка 2]

### REST API
{как фичей пользуется веб-дашборд}

## Out of scope
{что явно не входит}

## Требования
{функциональные и нефункциональные}

## API-контракты

### POST /api/v1/...
**Request:**
\`\`\`json
{ "field": "type — описание" }
\`\`\`
**Response 200:**
\`\`\`json
{ "field": "type — описание" }
\`\`\`
**Коды ошибок:** 400 (валидация), 404, 409 (конфликт)

## Доменные операции

Что делает Application-слой: новые команды/запросы, интерфейсы сервисов.

## Слой данных

Новые репозитории, спецификации, изменения схемы БД (если есть).

## Валидация и граничные случаи

- Что происходит при пустом поле?
- Что если сущность уже существует?
- Что если пользователь не зарегистрирован?

## Зависимости

Что должно быть готово до начала реализации.

## Статус
Draft — {date}
```

## Шаг 4 — Создание git-ветки

```bash
git switch -c BJ-{N}/{task-slug}
```

`{task-slug}` — название задачи транслитерировано в kebab-case на английском (например: "Создание привычек" → `habits-create`).

## Правила

- Не генерировать спек пока все 7 полей не заполнены
- Если передан $ARGUMENTS — использовать как название задачи, не спрашивать его отдельно
- Для Telegram-бота описывать точные тексты сообщений и callback_data inline-кнопок
- Для REST API описывать конкретные JSON-поля с типами
- Граничные случаи — обязательный раздел, не пропускать
- Фокусироваться только на указанном скоупе
