# /spec — Написать спецификацию фичи

Ты — технический аналитик для проекта BuJo.  
Напиши подробную спецификацию для фичи, описанной в аргументах: **$ARGUMENTS**

## Инструкции

1. Прочитай `CLAUDE.md` для понимания текущего состояния проекта.
2. Изучи существующий код, релевантный для фичи (доменные сущности, сервисы, контроллеры, Telegram-хендлеры).
3. Создай файл `.claude/specs/<feature-slug>.md` по шаблону ниже.
4. Название файла — kebab-case от названия фичи (например, `habits-create-list.md`).

## Шаблон спецификации

```markdown
# Спецификация: <Название фичи>

## Цель
Одно-два предложения — зачем эта фича нужна пользователю.

## Скоуп
Список того, что **входит** и **не входит** в эту задачу.

### Входит
- ...

### Не входит (отложено)
- ...

## Пользовательские сценарии

### Telegram-бот
Описание UX: какие команды, какие сообщения бот присылает, inline-кнопки, flow диалога.

Формат:
> **Пользователь:** `/команда`  
> **Бот:** "Текст ответа" + [Кнопка 1] [Кнопка 2]

### REST API
Описание того, как фичей пользуется будущий веб-дашборд.

## API-контракты

### POST /api/v1/...
**Request:**
```json
{ "field": "type — описание" }
```
**Response 200:**
```json
{ "field": "type — описание" }
```
**Коды ошибок:** 400 (валидация), 404, 409 (конфликт), ...

### GET /api/v1/...
...

## Доменные операции

Что делает Application-слой (сервисы/команды/запросы).  
Новые record-команды/запросы, интерфейсы сервисов.

## Слой данных

Новые репозитории, спецификации, изменения схемы (если есть).

## Валидация и граничные случаи

- Что происходит при пустом имени?
- Что если сущность уже существует?
- Что если пользователь не зарегистрирован?
- ...

## Зависимости

Что должно быть готово до начала реализации этой фичи.
```

## Правила

- Фокусируйся только на указанном скоупе, не расширяй задачу.
- Для Telegram-бота описывай точные тексты сообщений и callback_data inline-кнопок.
- Для REST API описывай конкретные JSON-поля с типами.
- Граничные случаи — обязательный раздел, не пропускай.
